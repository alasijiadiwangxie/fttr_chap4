# C1 AP 本地业务与队列观测

## 启用方式

| 配置键 | 默认值 | 含义 |
| --- | ---: | --- |
| `wifi.ap.observation.enabled` | `false` | 启用 C1 的窗口采样和逐包记录。 |
| `wifi.ap.observation.period.us` | `1000` | 采样周期，单位 μs，最小精度为 1 ns。 |
| `wifi.ap.observation.ewma.alpha` | `0.25` | 到达速率的 EWMA 权重，范围为 `(0, 1]`。 |

每台 SFU 持有独立的观测器。每个窗口为该 AP 输出 DL、UL 各四个 AC 的快照。窗口从仿真 0 ns 起算，首窗包含 0，其余窗口采用 `(start, end]`。边界同刻的协议事件及其零延时后续事件处理完毕后才发布快照。自然结束时结算非零长度的最后短窗，实际窗宽用作速率分母。采样时钟独立于 B2/B3 固定能耗窗口。快照可在 `SimulationContext.latestApTrafficObservation(sfuId)` 中只读取得，未启动或还没有完成首窗时返回空列表。

## 指标和状态口径

**下行**在报文经过光链路、进入 AP 的无线等待队列时才记一次本地到达。选定用于实际 DATA 发送时，每个 MPDU 从待发转为在途。解码成功时记业务交付，发送方收到 ACK 或 Block ACK 时将已确认成员从在途移出。`awaiting_confirm_packets` 是在途成员中已交付但仍在等待确认的子集。未确认且还可重试的成员回到等待队列。重试计数在重新开始实际传输时增加，重入队另有计数。最终丢弃从在途中移除。所有队列字节数采用用户报文大小。队首等待以原始 AP 入队时刻为起点，单位 ns，空队列取 `-1`。

**上行**只在 AP 成功解码 DATA 时观测到达和交付。UL 行的待发、在途、确认、重试和丢弃字段保持为零，队首等待为 `-1`。UL 行的两项速率都表示 AP 实际收到的业务。STA 私有缓存、STA 的重试状态以及因碰撞未解码的成员没有用于填充这些指标。

| 指标 | 计算口径 |
| --- | --- |
| 窗口到达和成功交付速率 | 分别依据本窗口内的事件数和字节数。包数 × 10⁹ ÷ 窗宽纳秒得到 packets/s，字节数 × 8000 ÷ 窗宽纳秒得到 Mb/s。跨窗排队会将报文的到达和交付分开。 |
| 下行交付成功比例 | 本窗确认数 ÷（确认数 + 最终丢弃数），按本窗完成结算的报文统计。分母为 0 或方向为 UL 时取 `-1`。 |
| EWMA 到达速率 | 首窗直接取实测速率，其余窗口使用 `α × 本窗实测速率 + (1 − α) × 上窗 EWMA`。packets/s 和 Mb/s 分开计算。 |
| 实际 TX/RX 时长 | 复用 AP 活动状态时序，对窗口和收发区间的交集按 ns 求和。半双工碰撞遵循已有 B2 活动归属。每个 AP 的同一窗口在八行里重复这两个字段，汇总时取一次。 |
| 平均聚合深度 | `MPDU 数 ÷ DATA PPDU 数`。单帧深度为 1，空窗为 0。DL 计实际启动的全部 DATA 成员，UL 计可解码 PPDU 的已解码成员。 |

逐事件 CSV 的 `WIFI_AP_QUEUE_EVENT` 行给出报文 ID、动作和该动作后的队列快照。`WIFI_AP_PPDU_OBSERVED` 行给出实际被观测到的 PPDU 深度。下行累计守恒关系为 **已到达 = 待发 + 在途 + 已确认 + 最终丢弃**。已交付未确认的成员仍属于在途，重入队不会再次增加到达量。

## 验证场景与方法

- 主矩阵覆盖静态 LCM/HCM、A‑MPDU 开关、轻载与饱和的 8 个组合。手动输入为 1500 B，四个 AC 循环。轻载有 8 个报文，AP 的光路到达分别包含 1 ms、2 ms 两个同刻边界。饱和场景以 20 μs 间隔发出 120 包，相当于输入期间 600 Mb/s。开启聚合时上限为 8 MPDU。
- 双 AP 场景在 HCM AP 1 的首批下行 4 个成员中显式令 ID 2、4 首次解码失败，LCM AP 2 同时产生上行接收。分别验证选择重传和重试上限为零时的丢弃。另一场景使同一 AP 的 DL、UL 竞争同刻开始，用来对账真实碰撞与重试。
- 各场景分别运行开启和关闭的 Java 仿真。原协议日志含实际交付、接入、时延、吞吐量、AP 活动和能耗摘要，移除新增的三类 C1 日志后逐行与关闭时对照。
- 脚本另从 SFU 入队、MAC 发送、接收、ACK、重传及丢弃事件重建逐包状态，从 B2 状态转换独立重算每个采样窗口的实际 TX/RX，并以包数、字节数和窗口宽度重算速率与 EWMA。完整配置、边界和事件顺序均能从 CSV 复核。

## 实测结果

11 组开启／关闭对照全部逐行匹配原协议轨迹和运行摘要，包含 **2,048** 条窗口行、**2,111** 条报文状态变化和 **326** 条 PPDU 观测。轻载 8 包全部交付，聚合开启后实测深度仍为 1。饱和对照的 120 包在自然排空前后的账本均通过逐包核对。

| 饱和场景 | DATA PPDU 数 | 最大实测聚合深度 | 采样中单 AC 峰值待发包数 | 最终确认包数 |
| --- | ---: | ---: | ---: | ---: |
| LCM，A‑MPDU 关闭 | 120 | 1 | 30 | 120 |
| LCM，A‑MPDU 开启 | 18 | 8 | 30 | 120 |
| HCM，A‑MPDU 关闭 | 120 | 1 | 30 | 120 |
| HCM，A‑MPDU 开启 | 22 | 8 | 30 | 120 |

在 HCM 轻载 BE 用例中，首包光路在 1000 μs 到达 AP，第一个窗口记录 1 包到达、队首已等待 0 ns、实测和 EWMA 均为 1000 packets/s，尚无交付。后续两个窗口无新增 BE 到达，EWMA 依次为 750 和 562.5 packets/s。使用实际自然结束时刻结算短窗，并逐窗口核对 TX/RX 交集。

部分 Block ACK 用例中，AP 1 的 BE 下行首帧收发隔着多个采样窗口。下表给出窗末在途账本和该窗的事件计数。最终四个成员各确认一次。重试上限为 0 的对照只丢弃失败的第 2、4 包。AP 2 的 UL 事件只在实际收到有效 DATA 时记录，两个 AP 的账本独立。

| 窗末（μs） | 在途 | 已交付待确认 | 本窗交付 | 本窗确认 | 本窗实际重传 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 4 | 0 | 0 | 0 | 0 |
| 200 | 4 | 2 | 2 | 0 | 0 |
| 300 | 2 | 0 | 0 | 2 | 2 |
| 400 | 2 | 2 | 2 | 0 | 0 |
| 500 | 0 | 0 | 0 | 2 | 0 |

另一个用例于 53 μs 发生同 AP 的 DL/UL 碰撞。AP 观测到本地实际发送占用和 DL 重传。未解码的 UL 首次发送未增加 AP 业务到达量，重传成功后只记录一次 UL 接收。

独立的 Maven 集成测试将 B2 能耗窗口截到 50.125 μs。HCM 的 2 MPDU 交换在 B2 窗内仅有 7,125 ns TX 和 0 ns RX。C1 的自然窗口则完整观测到 91,200 ns TX、32,000 ns RX，以及 182,200 ns 的确认。观测开关前后的 B2/B3 统计一致。

完整 Maven 回归 **436 项通过，0 失败、0 错误、0 跳过**。其中 C1 新增 7 项观测器单元测试、25 项集成测试。光侧冻结的 9 个场景轨迹全部匹配。

## 工程位置

`ApTrafficObserver` 归档各 AP 的本地计数和不可变快照。`Sfu` 从实际 MAC 发送、接收、确认与异常路径提供事件，`SimulationContext` 用协议时钟确定采样边界。AP 活动复用 `ApActivity`，C1 时长读取包含当前活动区间在窗内的部分。`ConfigLoader` 和 `SimulationConfig` 负责校验和传入参数，`TraceLogger` 负责输出数据。现有 EDCA、聚合装载、Block ACK、重传、PON/DBA 和功耗积分继续按原事件运行。
