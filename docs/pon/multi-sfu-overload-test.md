# 多 SFU、多 STA 的 DBA 过载对照

## 配置和可执行范围

对比 `giant-complete` 和 `rr-multi`。分别配置 4、8 台 SFU，每台连接 2 台 STA，业务在所有 STA 间均分。每台 STA 的各业务流独立按泊松过程到达，报文 1200 B。使用种子 101、202、303，每个 STA 的种子为 `种子 × 1000 + STA ID`。保留 VO→T1、VI→T2、BE→T3、BK→T4。固定 Wi-Fi 时延 0 μs，上行 2500 Mb/s、每帧 125 μs，光侧上行和 BWmap 下行传播分别为 10.025 μs、10 μs。

Java 分别拒绝将 Type 1 固定额度设置为 0，以及移除 Type 1 后令 VO 缺少映射。在严格保持业务映射的条件下，不能配置完全没有固定预约的纯 T4 实验。A′ 延用原映射和合法的 T1 固定配置，只发 BK。两种算法的配置只差 DBA 模式，GIANT 会实际预约空 T1 窗口，RR 不执行固定预约。对照中的空预约量单独计入。 [Java 配置拒绝结果](../../results/pon-multi-sfu-overload/pilot/pure-t4-config-check.csv)

| 组 | T1/T2/T3 全网输入 (Mb/s) | T4 全网输入 (Mb/s) | 用途 |
| --- | --- | --- | --- |
| A′ 仅 T4 发流 | 0/0/0 | 5000、8000 | 比较饱和吞吐、物理忙时及 SFU 公平性，保留 T1 固定预约 |
| B 高优先级隔离 | 60/80/100 | 0、5000、8000 | 以同输入的 T4=0 组测量过载对保护业务的影响 |

T1 固定额度、T2 保障额度和 T3 保障额度均为每 SFU 每 2 帧 1200 B，即每类每 SFU 38.4 Mb/s。T3 非保证额度另配每 2 帧 1200 B，T4 尽力而为额度每帧 38400 B。按 Java 的保守准入，把所有固定和保障额度视为同帧到期，再加 205 ns 控制时隙，4/8 台 SFU 分别需 46285/92365 ns，均小于 125000 ns。4/8 台 SFU 时，每类合计配置额度分别为 153.6/307.2 Mb/s，实际需求仍按相同全网输入均摊。因此规模对照同时改变了单对象负载、全网合计保障额度和轮询周期。

正式发流及观察采用 `[0,100 ms)`。在 `t<110 ms` 继续创建授权，以观测结束后的交付和剩余积压，已发出授权可完成结算。最大轮询周期为 4 ms，正式发流窗口包含 25 个完整周期。先进行四组 5 ms 试跑，Java 主进程峰值工作集约 93–102 MiB，原始日志约 5.6–8.2 MB/组。试跑后，在同一 20 ms 配置下比较了标准输出直接写文件和经缓冲管道写入，分别记录 33.16 s 和 13.68 s，生成的原始日志逐字节相同。正式采集保留已经完成的日志，剩余组使用缓冲管道续跑，最多同时 6 个 JVM，每 JVM 堆上限 512 MiB。 [规模试跑及实际配置](../../results/pon-multi-sfu-overload/pilot/scale-check.csv)

## 指标和对照口径

- 吞吐量以主窗口内实际交付给 MFU 的 DATA 字节数计算。光侧物理利用率使用实发 DATA 与实际 REPORT-only 发送时间之和除以 100 ms。授权利用率另采用真实预约窗口和控制时隙，空固定时隙及不可装包的帧尾预算可能只增加预约量。传播时间不增加发送占用。
- 每包发送时间为 3840 ns，每帧一个 205 ns 控制轮询后最多容纳 32 个整包。对应的满包 DATA 吞吐参考为 2457.6 Mb/s。在 A′ 中，若其余窗口都能装足，GIANT 每 2 帧为每 SFU 保留一个空 T1 包位，4/8 台时的理论参考分别降至 2304.0/2150.4 Mb/s。这些为容量计算参考，实测低于参考的部分由日志核查。
- FIFO 等待从光侧队列入队至实际装载。主窗口没有装载的包右截尾，截点 FIFO 积压、在途/后续交付、最终未交付分别记录。Jain 指数为 `(Σxᵢ)² / (N × Σxᵢ²)`，其中 `xᵢ` 为第 i 台 SFU 的实际交付吞吐，包含全部 N 台配置 SFU。另用各 SFU 的 T4 交付量计算同口径指数，全体都无交付时该项留空。
- 轮询每帧选一个 Alloc-ID。两种场景均为每台 SFU 四个 Alloc-ID，因此 4/8 台时每个对象的 REPORT-only 周期分别为 2/4 ms。预算结算也可能携带更新报告，即使预算实际装载了 0 包。现有模型不为结算报告增加独立发送时长。报告年龄从被 MFU 采用的本地快照算到决策，UNKNOWN 的次数单列。
- 固定或保证的配置额度、实际授权、实际发送分别核算。RR 的带宽交付与延迟同样测量；SI/AB 参考仅用于判断在相同配置目标下达成多少，RR 不执行 GIANT 的固定或保障阶段。实际输入低于配置额度时，实发字节应与实际业务量对照。

## 试验结果

60 组正式仿真共生成 3343608 个报文和 33459252 行 Java 日志。30 个 GIANT/RR 配对的生成时间、报文 ID、大小、业务及 STA 逐包一致。隔离组的六个「规模 × 种子」组合也跨 T4 负载核对了保护业务输入。所有运行通过共享 DATA/REPORT-only 时隙无重叠、发送与交付时序、报文守恒及预算结算检查。最多一组生成 86168 个包，正式运行最大 JVM 工作集约 592 MiB，最大单组原始日志 167.6 MB，正式归档压缩后合计 478.8 MB。

### A′ 仅 T4 发流，保留空 T1 固定预约

三种子等权平均。各双值列顺序为 GIANT / RR。物理忙时包括 0.16359% 的 REPORT-only 占用。

| SFU | T4 输入 (Mb/s) | 交付吞吐 (Mb/s) | 物理利用率 (%) | T4 Jain | 收尾后未交付 (包) |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 5000 | 2281.95 / 2426.59 | 91.45 / 97.24 | 0.9963 / 1.0000 | 26037 / 24370 |
| 4 | 8000 | 2283.36 / 2426.59 | 91.51 / 97.24 | 0.9964 / 1.0000 | 57179 / 55527 |
| 8 | 5000 | 2126.21 / 2423.55 | 85.22 / 97.12 | 0.9822 / 0.9996 | 27737 / 24319 |
| 8 | 8000 | 2128.77 / 2426.59 | 85.33 / 97.24 | 0.9823 / 0.9996 | 58889 / 55467 |

后半窗的交付吞吐在两个负载下均达到计算参考，GIANT 四/八台分别为 **2304.0/2150.4 Mb/s**，RR 均为 **2457.6 Mb/s**。主窗口均值包含冷启动。与其约 99% 的预约利用率相比，A′ 的 GIANT 物理利用率显著偏低。主要差额是四/八台 SFU 的空 T1 固定窗口，它们分别占主窗口的 **6.13%/12.26%**；RR 没有这项预约。增加 T4 输入主要转化成积压，在结束前没有清空。这里观测到的是持续过载下的交付速率，队列没有达到稳态。

在八台、8000 Mb/s 时，GIANT 各 SFU 的 T4 实际吞吐在全部种子中的范围为 **223.97–312.86 Mb/s**，RR 为 **294.62–313.34 Mb/s**。以每台 SFU 实际交付计算，RR 的 Jain 指数更接近 1。显式丢包计数为 0；表中积压均是尚未交付的报文。由于多数 T4 入队包在主窗口未装载，T4 的 FIFO 分位数只代表已装载样本，应连同截尾量阅读。

### B 高优先级隔离

与同规模、同种子、同策略的 T4=0 组比较。下表列 T4=8000 Mb/s，三类值按 T1/T2/T3 排列并取三个种子均值。5000 Mb/s 的对照也在配对差值 CSV 中。

| SFU | 策略 | T1/T2/T3 交付吞吐 (Mb/s) | P99 相对 T4=0 变化 (ms) |
| ---: | --- | --- | --- |
| 4 | GIANT | 61.34 / 77.06 / 98.62 | +0.000 / +0.000 / +0.000 |
| 4 | RR | 60.86 / 77.12 / 98.78 | +0.266 / +0.345 / +0.258 |
| 8 | GIANT | 62.02 / 76.61 / 99.20 | +0.000 / +0.000 / +0.000 |
| 8 | RR | 61.22 / 76.70 / 99.42 | +0.670 / +0.318 / +0.419 |

- **GIANT 的保护指标在两档 T4 过载下保持一致。** 每个规模和每个种子的 T1/T2/T3 交付吞吐、平均 FIFO 等待、P95 和 P99 均与自身 T4=0 组逐项相等。T1 到期固定预约达成率为 100%，其中约 40.0%（4 台）和 20.2%（8 台）的预约字节实际承载业务。T2/T3 按可见需求限定的保障授权与实发均达到 100%，未发现计时器、阶段顺序和可见需求下的保障短缺。报告时效仍影响绝对时延，例如 GIANT 饱和时的 T2/T3 P95 从四台的 **2.126/1.884 ms** 升至八台的 **3.505/3.457 ms**。
- **RR 在本负载下交付带宽变化小，尾部却变长。** 任一保护类在任一配对中的吞吐变化为 −0.384 至 +0.672 Mb/s，所有保护类在收尾后也都已交付。两档过载中每个配对的 P99 都上升，范围为 **0.035–0.707 ms**。RR 没有 T1 固定或 T2/T3 保障阶段。CSV 中 RR 的同一 SI/AB 参考用于衡量到期帧的覆盖，不能当作 RR 承诺的 SLA。
- **链路吞吐与隔离体现不同取舍。** B 组 8000 Mb/s 时，四台的总吞吐为 GIANT **2344.83**、RR **2427.71 Mb/s**；八台为 **2190.94**、**2427.04 Mb/s**。八台时 T4 Jain 分别为 **0.9687** 和 **0.9995**。本次 GIANT 的优势体现在相对自身基线的保护业务隔离，RR 的整体资源使用和 T4 公平性更高。

### 实际 REPORT Age 与服务间隔

在 A′ 的 8000 Mb/s 档，按所有已知 T4 决策样本加权，平均 REPORT Age 从四台到八台，GIANT 为 **254→472 μs**，RR 为 **292→518 μs**。实际 REPORT-only 周期为 **2→4 ms**，比平均报告年龄长，因为 DATA 预算结算也会刷新报告。T4 同一对象的平均预约间隔分别为 GIANT **373→736 μs**、RR **499→989 μs**；只计实际装载正字节的机会，分别为 **497→984 μs**、**499→989 μs**。GIANT 更短的预约间隔包含装不下整包的帧尾窗口。四台与八台都需要在每个周期轮询全部对象，规模变化也改变了每对象输入、合计保障额度和窗口次序，不能只用轮询周期解释时延变化。

### RR 与 GIANT 的在途预算对照

A′ 四台 SFU、T4=5000 Mb/s、种子 101 的目标帧 12 在 1375000 ns 决策。RR 的 Alloc-ID 104、204 分别已知 59402、143402 B，均仍有未结算预算；304、404 尚未收到报告。该帧 RR 没有产生 DATA 授权（原始日志第 5041–5054 行）。同一输入下，GIANT 对 104、204 的已知净需求为 42000、148202 B，前序预算同样未结算。完整模式生成 38400 B 和 598 B 两个预约，其中前者实际发 32 包，后者装不下队首 1200 B 报文，结算为 0 B（第 5609–5646、7081、7105 行）。这组事件说明未结算跳过与流水授权确实会改变服务机会，也说明非零预算不能直接用于计算吞吐。对应两条原始日志可用场景名 `t4-only-input-4sfu-5000mbps-101-*` 在索引中定位。

B 组八台 SFU、T4=5000 Mb/s、种子 101 的 GIANT 目标帧 33 预约顺序是八份 T1 固定、三份 T2/T3 保障，再给 T4 Alloc-ID 204 剩余的 25798 B。三份保障各实际发送 1200 B，T4 实际发送 25200 B，八份固定窗口中只有一份承载 DATA。DATA 预约和控制共占 124999 ns，仍在 125000 ns 的帧内。可查 `isolation-8sfu-5000mbps-101-giant-complete` 原始日志第 22906–22931 行及第 23818–24564 行。

## 复现

在仓库根目录运行。Maven 依赖未缓存时去掉 `-o`。先试跑，再执行正式仿真、统计和绘图。

```powershell
mvn -o -DskipTests package
python -B tools/run_pon_multi_sfu_overload.py --pilot --jobs 2
python -B tools/run_pon_multi_sfu_overload.py --jobs 6
python -B tools/plot_pon_multi_sfu_overload.py
mvn -o '-Dtest=GiantCompletionTest,PonMultiGrantDbaTest,PonReportPollingTest,GiantPipelinedLedgerTest' test
```

也可先运行 `--capture-only` 采集，再用 `--reuse-raw` 重建统计。中断后可加 `--resume-capture`，保留配置和构建匹配的已完成档案。原始日志和校验回执位于本地结果目录的 `raw/`，可由相同配置重新生成。30 项相关 Java 测试通过。
