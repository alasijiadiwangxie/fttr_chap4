# GIANT T2 保障额度与 FIFO 等待

## 配对配置

沿用 [3050 Mb/s 过载配置](dba-qos-comparison.md) 的业务比例和物理条件。两台 SFU 每台一台 STA，VO→T1、VI→T2、BE→T3、BK→T4。全网四类期望输入为 244 / 305 / 549 / 1952 Mb/s。每 AC 独立泊松到达，报文 1200 B。上行 2500 Mb/s、125 μs 帧，每帧轮询一台 SFU，64 B REPORT-only 时隙占 205 ns。上行传播 10.025 μs，下行传播 10 μs。无线使用固定 0 μs 时延。

每个种子（101、202、303）分别运行 GIANT `ABmin=2400/3600/4800 B` 与 RR 一次。三档 GIANT 只改 Alloc-ID 102、202 的 ABmin，SImax 均为 1。RR 用同一份 2400 B 描述，策略按 REPORT 有效需求和剩余容量授权。RR 数据是单独基线，绘图在三个横坐标显示同一条参考线。

| GIANT T2 ABmin，每 SFU | 一次可装整包数 | 单 SFU 名义额度 | 全网名义额度 | 单 SFU 输入 / 名义额度 | 同帧固定+保障+控制的最坏预留 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2400 B | 2 | 153.6 Mb/s | 307.2 Mb/s | 99.28% | 46285 ns |
| 3600 B | 3 | 230.4 Mb/s | 460.8 Mb/s | 66.19% | 53965 ns |
| 4800 B | 4 | 307.2 Mb/s | 614.4 Mb/s | 49.64% | 61645 ns |

单 SFU T2 期望输入为 152.5 Mb/s，即平均每帧 2382.8 B。上表的最坏预留包含两个 T1 固定预约、两台 SFU 的 T2/T3 保障额度和 64 B 控制时隙，均满足 125000 ns 帧容量。GIANT 本场景为 T2 每帧提供一次保障机会，实际授权仍受已知需求约束。随机到达量可能超过一帧额度，即使长期输入低于额度也会产生排队。

## 观察窗口和判据

发流及主观察窗口为 `[0,100 ms)`，是上一轮的四倍。之后停止发流，允许在 `t<110 ms` 继续调度，已创建时隙和结算自然执行完。配对逐包比较生成时间、ID、源、AC、大小。运行同时核对 BWmap、DATA、结算、FIFO 顺序和 REPORT 有效需求。

- FIFO 等待从入队到本地装载，以 100 ms 前装载的报文为样本。抖动为样本标准差，P95 和 P99 用最近秩。窗口内未装载报文单列数量和最大等待年龄，收尾后的剩余积压按报文状态记录。
- 吞吐按 MFU 在主窗口实际交付的字节计。授权量、已用量和未用量按主窗口内完整目标帧的结算计，和交付吞吐有不同事件边界。统计取自 Java 的入队、装载、授权、结算及 MFU 交付事件。
- 逐帧记录 MFU 的已有报告、有效已知需求、同一 Alloc-ID 的前序在途预约、保障到期与授权量。同时离线重建决策时、本帧首和帧末真实 FIFO。FIFO 中尚未装载的包可能已经被上一笔预约覆盖，判定可见性差距时应先扣除这部分。
- 额度限制帧需同时满足已知需求超过 ABmin、该帧授权和实发均达到 ABmin、装载后仍有积压。报告可见性差距以决策时 FIFO 字节扣除前序尚未装载的预约后，仍高于 MFU 有效已知量来识别。决策之后到队的报文另属提前规划的时间差。保障阶段的请求、授予和实际使用分别核账。
- 用发流期间四个连续 25 ms 区段观察 T2 FIFO 的队长和积压帧。收尾的清空速度与持续发流时的走势分别解释。有限窗口与三个种子给出的是实测稳定性迹象。

## 结果与证据

### T2 时延和吞吐量

表内为三个种子的等权平均。两个 SFU 的 T2 报文先按种子汇总，再计算该种子的时延指标。每个种子有 3133–3268 个 T2 时延样本。两个积压列使用 100 ms 截点前的光侧 FIFO，峰值取窗口内两台 SFU 合计队长的峰值。

| 策略 | 平均等待 (ms) | P95 (ms) | P99 (ms) | 抖动 (ms) | 交付吞吐 (Mb/s) | 已授权 / 实发 (MB) | 峰值 / 截点积压 (包) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| GIANT 2400 B | 1.958 | 4.135 | 4.619 | 1.086 | 302.272 | 3.77840 / 3.77840 | 113.0 / 76.7 |
| GIANT 3600 B | 0.391 | 0.654 | 1.076 | 0.148 | 308.128 | 3.85160 / 3.85160 | 35.3 / 15.7 |
| GIANT 4800 B | 0.362 | 0.537 | 0.962 | 0.124 | 308.032 | 3.85040 / 3.85040 | 35.7 / 16.7 |
| RR | 0.531 | 0.713 | 0.767 | 0.118 | 307.904 | 3.84960 / 3.84880 | 37.0 / 18.0 |

从 2400 B 调到 3600 B，平均等待降低 80.0%，在三个配对种子中均低于 RR。4800 B 继续降低平均等待约 0.029 ms 和 P99 约 0.114 ms，两档的 P99 仍在三个种子中均高于 RR。2400 B 档在截点尚未装载的报文最多，被截尾报文在个别种子中已等待约 4.936 ms。时延分位数只反映已装载样本，须结合积压列解读。完整的 T1–T4 及逐 Alloc-ID 指标见 [metrics.csv](../../results/pon-t2-delay/metrics.csv)。

### 区分额度限制、REPORT 滞后与授权执行

每档有 4788 个观测样本，每个样本对应一个 Alloc-ID 在一个完整目标帧的决策，涵盖三个种子。从已收到有效 REPORT 的样本计算平均 REPORT Age。可见性列另要求已知需求低于该配置的 ABmin，门槛随档位变化，因此跨档频数本身不能衡量报告机制变好或变差。

| 策略 | 额度限制帧 | 可见性差距且已知量低于本档额度 | 平均 REPORT Age (μs) | 最长连续帧末有积压 (帧) |
| --- | ---: | ---: | ---: | ---: |
| GIANT 2400 B | 4668 (97.5%) | 40 | 99.3 | 798 |
| GIANT 3600 B | 1589 (33.2%) | 1972 | 122.0 | 798 |
| GIANT 4800 B | 668 (14.0%) | 2990 | 129.6 | 770 |
| RR | 不适用 | 不适用 | 194.4 | 798 |

1. **2400 B 的主要瓶颈是服务额度。** 每 SFU 平均输入为名义额度的 99.28%。实测六个「种子 × SFU」输入中有三个超过 153.6 Mb/s，分别为 159.360、155.520 和 158.112 Mb/s。即使其余三个低于额度，泊松到达也让队列长时间保持有积压。种子 101、Alloc-ID 102 的目标帧 5 在 **500000 ns** 决策。四组的有效已知需求均为 **3600 B**，2400 B 档只授权并发送 **2400 B**，其余三组都发 **3600 B**。同一 Alloc-ID 到目标帧 551 时，2400 B 档已知需求 **111600 B**，仍只能发 **2400 B**，装载后剩 **95 包**。两例中 MFU 已看到超额需求。
2. **放宽 ABmin 后仍存在 REPORT 可见性限制。** 种子 101、Alloc-ID 202 的目标帧 15，4800 B 档在 **1750000 ns** 决策。最新报告于 **1671285 ns** 快照、**1681310 ns** 到达，报告 **8400 B**。扣除前序未结算的 **4800 B**，MFU 只知 **3600 B**。当时实际 FIFO 有 **10800 B**，扣除尚未装载的前序预约后仍有 **6000 B**。本次授权和实发均为 **3600 B**，装载后还剩 **4 包**。这是同一帧内无法用满 4800 B 的可核查实例。三档 GIANT 平均报告年龄随额度增加而上升，平均等待同时下降。报告年龄受发送和报告时机共同影响，实验没有独立改变反馈延迟，尚不能用平均年龄解释与 RR 的 P99 差异。
3. **本组未发现 T2 保障申请被容量竞争截断或已发预算执行失败。** 三档的保障申请与授权短缺均为 **0 B**，已知需求限定后的保障字节达成率均为 **100%**，T2 未用预算均为 **0 B**。RR 另有 **192** 个样本在有正已知需求时因在途未结算而未获新授权，这是现有策略条件。若进一步追查高档 GIANT 的尾延迟，可先从 [PonDemandLedger.estimateAllocation](../../src/main/java/edu/suda/fttr/entity/PonDemandLedger.java#L42) 对照 REPORT 到达和在途扣减，再在 [Mfu.planDbaExecution](../../src/main/java/edu/suda/fttr/entity/Mfu.java#L223) 查看该帧可见需求，随后定位 [GiantDbaPolicy.allocate](../../src/main/java/edu/suda/fttr/dba/GiantDbaPolicy.java#L116) 的阶段额度。本次保留这些机制，后续可单独扫描报告时效验证尾部影响。

在 [t2-grant-trace.csv](../../results/pon-t2-delay/t2-grant-trace.csv) 中按种子、额度、Alloc-ID 和目标帧筛选。目标帧 551 的状态、决策和装载分别在该原始日志的第 **280367、280376、281010** 行，4800 B 档目标帧 15 对应第 **5651、5657、6342** 行。原始文件由 [raw-index.csv](../../results/pon-t2-delay/raw-index.csv) 定位。

### 发流期间是否趋于稳定

下表为连续四个 25 ms 区段内，两个 SFU 合计 T2 FIFO 在帧首的平均包数，再对三个种子等权平均。

| 策略 | 0–25 ms | 25–50 ms | 50–75 ms | 75–100 ms |
| --- | ---: | ---: | ---: | ---: |
| GIANT 2400 B | 37.7 | 53.0 | 88.6 | 79.0 |
| GIANT 3600 B | 14.3 | 14.7 | 13.2 | 13.7 |
| GIANT 4800 B | 13.0 | 13.7 | 12.6 | 13.0 |
| RR | 18.2 | 19.2 | 18.4 | 18.4 |

2400 B 在三个种子中，最后 25 ms 的平均队长均高于最初 25 ms。3600 B 和 4800 B 未呈现相同的持续上升，尽管单个 FIFO 可连续多帧保持非空。停止发流并完成收尾后，所有档位的 T2 均已排空。是否清空和是否有增长趋势分别依据收尾及发流期间的事件判断。有限种子和窗口仍只能给出经验结论。[25 ms 分段统计](../../results/pon-t2-delay/t2-window-summary.csv) · [5 ms 积压趋势图](../../results/pon-t2-delay/figures/t2-backlog-over-time.svg)

### 其他业务的资源影响

各单元格为「MFU 实际交付吞吐 Mb/s / 实际授权 MB」，同样取三个种子均值。

| 策略 | T1 | T3 | T4 |
| --- | ---: | ---: | ---: |
| GIANT 2400 B | 242.368 / 3.83040 | 545.152 / 6.81440 | 1283.808 / 16.52482 |
| GIANT 3600 B | 242.368 / 3.83040 | 545.120 / 6.81400 | 1278.176 / 16.45442 |
| GIANT 4800 B | 242.368 / 3.83040 | 545.120 / 6.81400 | 1278.400 / 16.45722 |
| RR | 241.664 / 3.02080 | 544.480 / 6.81916 | 1100.160 / 14.06975 |

T1 固定预约达成率和 T3 已知需求限定后的保障实发率三档均为 100%，T1 平均等待始终为 0.162 ms，T3 为 0.455–0.457 ms。T4 使用剩余资源，上调 T2 额度后其窗口吞吐减少约 **5.4–5.6 Mb/s**，P99 从 34.395 ms 升到 35.093–36.125 ms。GIANT 各档的 T4 收尾积压仍有约 4756–4759 包，RR 约 7144 包。日志的显式丢包计数为 0，积压按未交付报文单独核算。

## 结论

本场景优先采用每 SFU **3600 B、SImax=1**。它从每帧两个包提高到三个包，显著缓解额度限制，发流窗口内未再出现同样的积压增长趋势。T1/T3 的保障达成率保持不变，T4 有少量吞吐和尾时延代价。**4800 B** 可作为对 GIANT 尾时延更敏感时的候选，平均收益已明显收窄。如果验收要求 T2 的 P99 也低于 RR，两档均未达到，需要针对配对尾包事件和报告可见性做独立验证。

## 复现

在仓库根目录使用 JDK 11+、Maven 和 Python 3.10+。Maven 依赖已缓存时可离线构建，首次构建可去掉 `-o`。

```powershell
mvn -o -DskipTests package
python -B tools/run_pon_t2_delay.py
python -B tools/plot_pon_t2_delay.py
```

12 次 Java 运行使用同一构建，三个种子的生成流各自在四组间逐包相同。种子 101、202、303 的每组输入分别为 **31885、31758、31643 包**。校验还包括 FIFO 顺序、授权守恒（授权 = 实发 + 未用）、逐包交付守恒、T2 有效已知需求复算，以及逐帧授权合计与指标表一致。Maven 打包通过，本轮执行专项仿真，未运行完整 Maven 回归。

结果写到 `results/pon-t2-delay/`。实际配置、压缩事件日志和输入校验值由 `raw-index.csv` 对应。仅重算本次已归档事件时用 `python -B tools/run_pon_t2_delay.py --reuse-raw`。原始日志和运行回执留在本地 `raw/`，也可用上面的完整命令重新生成。此次修改限于实验、统计、绘图和交付材料。
