# GIANT 与 RR DBA 的时延、SLA 和丢包实验

本实验使用现有 `giant-complete` 与 `rr-multi`。Java 策略、队列、PON 时隙、BWmap、REPORT 和无线实现均沿用当前版本。实验只新增配置生成、事件归档、统计与绘图。

## 场景与配对

两台 SFU 各接一台 STA，每台 SFU 的 VO、VI、BE、BK 分别进入 Type 1、2、3、4，对应 Alloc-ID 101–104 和 201–204。每个 STA 分担一半业务，每 AC 是独立泊松流，报文统一 1200 B。上行 2500 Mb/s，帧长 125 μs，BWmap 下行和上行传播分别为 10 μs、10.025 μs，每帧保留一个 64 B REPORT-only 窗口。无线使用固定 0 μs 时延，以单独观测光侧等待。

| 场景 | T1 输入 | T2 输入 | T3 输入 | T4 输入 | 总输入 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 轻载 | 20 | 25 | 45 | 160 | 250 |
| 中载 | 100 | 125 | 225 | 800 | 1250 |
| 接近线速 | 184 | 230 | 414 | 1472 | 2300 |
| 过载 | 244 | 305 | 549 | 1952 | 3050 |
| T4 隔离 | 100 | 125 | 225 | 300 / 1800 / 2700 | 750 / 2250 / 3150 |

速率单位为 Mb/s，表值为配置的期望流量。种子 101、202、303。一般负载下两种策略的生成时刻、报文 ID、源 STA、AC、长度都逐项相同。隔离组同样逐对比较策略，并核对不同 T4 档位下的 T1/T2/T3 到达时刻、源、AC 和长度。跨档时 T4 的包数会改变全局报文编号，因此隔离组跨档只比较这些高等级流的内容和时序。

每台 SFU 的 T1 固定、T2 保障、T3 保障均为每帧 2400 B。T3 非保证额度为每帧 2400 B，T4 尽力而为上限为每帧 38400 B。两台 SFU 的 T1 固定、T2 保障、T3 保障名义带宽各为 307.2 Mb/s。一帧的固定与保障合计预留上限为 46080 ns，加轮询为 46285 ns，低于 125000 ns。这里用不同的资格和实际发送指标检验保障，业务吞吐达到名义额度仍取决于需求发现、负载与整包装载。

## 统计窗口与依据

统一从 0 到 25 ms（不含右端点）生成业务并观测，纳入启动期。继续调度至 30 ms（不含右端点），之后已有授权、传播和结算完成。期末仍无交付或终止丢包事件的报文记为积压。吞吐量按主窗口内 MFU 交付字节计算。以帧为单位的 SLA 指标仅使用主窗口内的完整目标帧。

- **FIFO 排队时延**为 `PON_DBA_FILL` 选中报文的时刻减去 `TCONT_ENQUEUE`。主统计包含在 25 ms 前移出 FIFO 的报文，真实交付可发生在观察窗口后。抖动为这些等待值的样本标准差，样本数小于 2 时留空。P95、P99 和 P99.9 使用最近秩。尾部期望样本数 `n(1−p)` 小于 1 标为不可分辨，小于 10 标为尾部样本少。最大值是观察样本最大值，仍在 FIFO 的报文另列截止时的等待年龄。
- **SLA**区分配置周期额度、已发授权和实际承载。完整 GIANT 的固定预约包括没有需求的周期。保障满足率按 MFU 的已知有效需求限定到期分母，未知机会另列。合并时隙的实发字节先归因固定、保障，再归因非保证和尽力而为，统计不把容量归因为带阶段标签的报文。RR 的原生阶段字段留空。两策略另按同一离线周期基准观察授权和服务，T2/T3 当帧预期取配置额度与帧首实际待装载字节的较小值，因而能观察 REPORT 迟到及在途账本造成的服务缺口。该离线基准没有参与 Java 调度。
- **丢包、积压和公平性**由逐包及逐预算事件计算。终止丢包为 `WIFI_COLLISION_DROP` 或 `WIFI_RETRY_LIMIT_DROP`，比率分母是发流窗口全部生成报文。FIFO 峰值按入队与装载重建，同刻加减合并，因此排除只存在于零时长事件间的瞬时峰。多个 SFU 的同类型队列合计峰值来自同一时刻。Jain 指数按同类型两台 SFU 的实际主窗口吞吐计算。

## 队列溢出支持

当前 PON 待授权 FIFO 使用 `ArrayDeque`，入队直接 `addLast`，未配置容量或溢出事件（`PonUplink.java` 的 `Port.enqueue` 与 `LocalQueue`）。无线发送队列也没有此类限制（`Sfu.java` 的入队路径）。因此，CSV 的溢出包数、溢出率为空并标记 `unsupported`，图中用 N/A 标出。当前只测量显式终止丢包和积压，它们采用独立计数。

## 结果与异常

42 个正式场景完成。21 组策略输入相同，隔离组每个种子的非 T4 流跨档一致。接近线速的 GIANT 三个种子独立重放，原始 Java 日志一致。三组 CSV 各 504 行，每个场景提供 4 个类型汇总和 8 个 Alloc-ID 明细。如下数值均为三个种子的算术平均。图中保留种子间范围。

### FIFO 时延与尾部分位数

3050 Mb/s 过载点的结果如下。每格为 **GIANT / RR**，单位 ms。

| 类型 | 平均 | P95 | P99 | P99.9 | 样本最大 | 抖动 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| T1 | 0.134 / 0.532 | 0.317 / 0.717 | 0.395 / 0.807 | 0.477 / 0.999 | 0.477 / 0.999 | 0.091 / 0.121 |
| T2 | 1.157 / 0.533 | 1.773 / 0.716 | 1.887 / 0.830 | 2.000 / 1.046 | 2.000 / 1.046 | 0.376 / 0.122 |
| T3 | 0.527 / 0.526 | 1.161 / 0.709 | 1.343 / 0.895 | 1.417 / 1.252 | 1.425 / 1.292 | 0.281 / 0.131 |
| T4 | 5.052 / 5.554 | 8.726 / 13.416 | 9.244 / 15.152 | 9.396 / 15.512 | 9.441 / 15.516 | 2.389 / 3.867 |

三个种子分别计算分位数后再平均。168 条逐类型统计中，P99.9 有 126 条不可分辨、42 条尾部样本少。T1/T2 的过载 P99.9 退化为样本最大值。T4 在主窗口内的 FIFO 装载覆盖率只有 63.55% / 53.64%，因此 T4 分位数是已装载样本的描述，未装载等待和最终积压须同时阅读。CSV 中保留了样本数、标记及未装载的最大等待年龄。

在过载点，GIANT 的 T2 比 RR 等得更久，主窗口实际吞吐也较低（290.56 对 299.01 Mb/s）。种子 101 的 Alloc-ID 202 报文 4384 于 13727000 ns 入队，15773245 ns 由 D834 装载，等待 2046245 ns。D834 只装入配置额度内的 2400 B，装载后仍积压 25 包。同一运行中，202 在 198 个完整目标帧中有 191 帧的有效已知需求超过 2400 B。T2 的配置带宽仅略高于平均输入，泊松突发需跨帧消化。RR 的已知需求可按剩余容量成批申请，因此在该案例先排空 T2 的部分突发。

### SLA、剩余带宽和隔离

GIANT 的 T1 固定预约满足率在全部正式场景中为 **100%**。两台 SFU 一共配置 307.2 Mb/s，主窗口实际固定承载从轻载的 21.89 Mb/s 增至过载的 242.18 Mb/s。空固定窗的使用不足与预约违约分列。RR 可使用相同业务配置，实际交付可对照，其固定与保障阶段字段留空。

GIANT 的 T2/T3 在 MFU 已知需求满足资格的到期机会中，授权与实发归因均为 **100%**，计数器或额度违规与阶段倒置均为 **0**。共同离线基准覆盖更严格的本地 FIFO 需求。在 3050 Mb/s 下，T2/T3 实际覆盖率为 GIANT **95.74% / 94.02%** 和 RR **32.17% / 32.66%**，GIANT 每次平均仍有 **19.33 / 30.33** 个到期窗口未覆盖离线需求。轻载 GIANT 的离线覆盖率为 **20.15% / 21.00%**。轻载种子 101 的 Alloc-ID 203 在 250000 ns 决策时已有 1 包入队，目标帧 3 到期但 `assured_reason=UNKNOWN`。这是可见性差距。离线基准也包含在提前决策后、目标帧开始前进入 FIFO 的报文。

过载时，GIANT 剩余预算约 **16.7% 给 T3 非保证、83.3% 给 T4 尽力而为**。每次运行平均分别实发归因 800800 B 和 3882000 B。配置的组件上限、授权预算和实发归因在 CSV 中单列。T4 的同级 Jain 指数范围为 **0.99952–0.99984**，三种子的连续实发最大间隔均为 2 帧，两个 Alloc-ID 最终均有积压。

隔离组将 T4 从 300 增到 2700 Mb/s，T1/T2/T3 输入保持相同。主窗口内：

| 策略 | T1 吞吐（Mb/s） | T1 平均等待 / 抖动（ms） | T2 吞吐（Mb/s） | T2 平均等待 / 抖动（ms） |
| --- | ---: | ---: | ---: | ---: |
| GIANT，T4 300 → 2700 | 101.38 → 101.38 | 0.073 / 0.043，两端相同 | 125.31 → 125.31 | 0.494 / 0.217，两端相同 |
| RR，T4 300 → 2700 | 99.71 → 98.56 | 0.488 / 0.217 → 0.574 / 0.190 | 125.82 → 125.31 | 0.441 / 0.193 → 0.546 / 0.157 |

GIANT 两个保护类型的中间档也一致。RR 的均值等待变长，样本标准差在该隔离实验中下降。隔离结果说明本配置下 T4 过载未挤占已具备资格的 GIANT 保障，且独立于负载扫描中同时抬高 T2 输入造成的等待。

### 丢包与积压

两种策略在 42 次运行中的显式终止丢包均为 **0**。固定无线时延配置绕过了竞争和重试路径，此处的零丢包只适用于实际运行配置。3050 Mb/s 下，T1–T3 均在收尾后清空。T4 的合计峰值 FIFO 为 GIANT **1858**、RR **2360.33** 包，最终未交付积压为 **767.67 / 1494.33** 包。T4 隔离的最高压力下积压分别为 **1465.67 / 2701.33** 包。上述报文仍保留在队列中。

### 问题位置与后续复核

| 未达到或不可测的目标 | 当前证据 | 建议检查位置 |
| --- | --- | --- |
| 到期真实 FIFO 需求均能按时覆盖 | 离线 T2/T3 覆盖低于 100%，见轻载 250000 ns 的 UNKNOWN 和过载点的离线短缺 | 对齐 `Mfu.planDbaExecution` 的可见报告、`PonDemandLedger.estimateAllocation` 的在途扣减和 `PonUplink` 的轮询周期 |

## 复现

在仓库根目录以 JDK 11+、Maven 和 Python 3.10+ 运行。以下命令仅构建当前 JAR 并执行本专项。

```powershell
mvn -o -DskipTests package
python -B tools/run_pon_qos_special.py
python -B tools/plot_pon_qos_special.py
```

默认输出 `results/pon-dba-qos-comparison/`。其中 `raw-index.csv` 对应每次实际配置、输入哈希、Java 构建标识和压缩日志。原始日志存于同目录 `raw/`，可由运行命令重新生成。只重算现有事件时使用 `python -B tools/run_pon_qos_special.py --reuse-raw`。
