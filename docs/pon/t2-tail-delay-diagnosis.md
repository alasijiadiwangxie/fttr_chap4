# T2 尾时延的服务间隔与 REPORT 时效诊断

## 配对设计

沿用 [3050 Mb/s 过载实验](t2-delay-analysis.md)。两台 SFU，每台一台 STA，VO→T1、VI→T2、BE→T3、BK→T4。总期望输入分别为 244、305、549、1952 Mb/s，各业务独立泊松到达，报文均为 1200 B。上行 2500 Mb/s、帧长 125 μs，REPORT 和数据上行传播 10.025 μs，BWmap 下行传播 10 μs，无线仍使用固定 0 μs 时延。

| 组 | 策略 | T2 SImax | T2 ABmin / SFU | 每次 T2 机会最多装包 | REPORT-only 全局轮询 |
| --- | --- | ---: | ---: | ---: | --- |
| SI1 | GIANT | 1 帧 | 3600 B | 3 | 每帧 1 次 |
| SI2 | GIANT | 2 帧 | 7200 B | 6 | 每帧 1 次 |
| RR | RR 多授权 | — | — | 取决于已知需求与剩余容量 | 每帧 1 次 |
| Poll4 | GIANT | 1 帧 | 3600 B | 3 | 每 4 帧 1 次 |

两档 GIANT 的名义保障均为 230.4 Mb/s/SFU，实际使用受服务计数器、已知需求和时隙约束。若两台 SFU 的 T2 同时到期，连同 T1 固定预约、T3 保障和控制时隙，SI1、SI2 最多分别占 53965、77005 ns，均可装入 125000 ns 帧。RR 配置文件保留与 SI1 相同的 T-CONT 描述，RR 策略不使用其 SI 或 AB 决定实际授权。

同一种子（101、202、303）的四组输入逐包核对时间、ID、源、业务类型和长度。发流和主统计窗口均为 `[0,100 ms)`，允许在 `t<110 ms` 继续创建服务计划及轮询，已发授权执行至结算。各组共用相同截点；额外报告以 5 ms 后入队的报文为同口径样本，仍保留 100 ms 截尾。

## 统计与证据口径

- FIFO 等待从光侧入队到从本地 FIFO 装载，抖动取样本标准差，P95/P99 取最近秩。入队但未能在 100 ms 前装载的报文列为截尾，积压按报文数另列。吞吐量以主窗口收到的 MFU DATA 为准。
- 服务间隔以同一 Alloc-ID 两次实载正字节的时隙起点之差计算，同时记录跨过多少目标帧。达到 SI 计数器到期是一种服务机会。能否实发取决于该次需求及合法授权。
- MFU 的有效已知需求从最近接受的 REPORT 复算。对于快照后才开始的预约，未结算时扣预算，已结算时扣实发。对比真实 FIFO 时也列出尚未装载的前序预约，再看未被预约覆盖的队列。队列和报文位置只在离线分析中重建。
- 每个种子用 SI1 与 RR 各自的 P99 门槛选择尾包，再按 ID 取并集，同一 ID 在两组都追踪。表中把入队、预算决策、BWmap 发/收、时隙装载、单包发送与 MFU 到达分别标记。若授权在报文入队之前已发出，入队前的时间不计入该报文等待。
- 一个报文可能同时遇到多个约束。逐事件判断使用决策当时的 FIFO 排名、报告快照及扣减、计数器和目标帧预算；各原因出现次数可以重叠。MFU 只有字节总量，描述单个报文是否处于可覆盖范围时以 FIFO 前缀作离线判断。
- T-CONT 拓扑有 8 个 Alloc-ID，每次控制轮询按顺序选其中一个对象。全局间隔为 1 帧或 4 帧时，单对象探测周期分别为 1 ms 和 4 ms。实际 REPORT 还可能随 DATA 结算到达。统计使用执行过的 64 B 控制时隙，每个 205 ns，传播时间不计为忙时。轮询频率会同时改变冷启动相位、快照时机和控制占用，这组是轮询敏感性对照。

## SI、轮询与积压

表内时延和积压取三个种子的等权平均。截点积压是两台 SFU 的 T2 在 100 ms 时尚未装载的报文数。

| 组 | 平均 FIFO 等待 (ms) | P95 (ms) | P99 (ms) | 抖动 (ms) | 截点积压 (包) | 去掉前 5 ms 入队后的 P99 (ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| SI1 | 0.391 | 0.654 | 1.076 | 0.148 | 15.7 | 1.068 |
| SI2 | 0.401 | 0.605 | 1.040 | 0.137 | 14.0 | 1.015 |
| RR | 0.531 | 0.713 | 0.767 | 0.118 | 18.0 | 0.755 |
| Poll4 | 0.837 | 2.860 | 3.544 | 0.859 | 22.7 | 3.550 |

**相同保障速率下，SI2 的平均等待高约 10 μs，P95 和 P99 分别低约 49 μs 和 36 μs。** 三个种子方向一致。SI2 将两个服务机会合并为一个更大的批量，真实服务间隔变长。已知需求超过额度、额度全部实发且装载后仍有积压的样本从 1589 降为 443。SI1 和 SI2 的合计帧首队长在四个 25 ms 区段内约为 13–15 包，均未见持续增长。RR 的平均等待较长，但两种 GIANT 配置的 P99 仍高于 RR。只将 SI1 改成 SI2 未消除这项差距。

| 组 | 正字节服务次数 | 服务间隔均值 / P95 / 最大 (μs) | 决策时报告年龄均值 (μs) | 决策时真实 FIFO / 扣前序预约后 / MFU 已知均值 (B) |
| --- | ---: | ---: | ---: | ---: |
| SI1 | 4021 | 147.7 / 250.0 / 1621.2 | 122.0 | 8393 / 5982 / 3606 |
| SI2 | 2295 | 259.1 / 261.5 / 1488.5 | 157.2 | 8510 / 6101 / 3085 |
| RR | 1576 | 377.8 / 398.0 / 1488.5 | 194.4 | 11105 / 8693 / 4957 |
| Poll4 | 3782 | 155.1 / 250.0 / 4375.0 | 265.2 | 17022 / 14616 / 9434 |

每组共 4788 个 Alloc-ID×目标帧样本。服务间隔汇总所有相邻正字节服务对。报告年龄与已知均值只用 KNOWN 样本，真实 FIFO 两列含全部样本，UNKNOWN 在 CSV 中单列。SI2 有 2394 次明确的 `NOT_DUE`，其中 442 次当时已知需求为正。看到的需求低于未覆盖 FIFO 的帧数为 SI1 的 3842、SI2 的 4011。服务间隔和报告年龄较短并不保证更低的尾时延，RR 在获得预算时可以一次装入更多报文。

SI2 中，种子 101、Alloc-ID 102 的目标帧 58 已知 **3600 B**，计数器 **2→1**，日志明确标记 `NOT_DUE`。下一目标帧已知 **8400 B**，计数器 **1→2**，授权和实发 **7200 B**。这是同一对象连续两帧的 SI 门控证据，可查 SI2 原始日志第 **27185、27660、28297** 行。

**放慢轮询会放大尾时延。** 每个种子内，SI1 执行 798 个控制时隙，占 163590 ns（主窗口的 0.16359%）；Poll4 执行 200 个，占 41000 ns（0.04100%）。控制占用减少时，T2 的 P99 仍由 1.076 ms 增至 3.544 ms，最长实发间隔增至 4.375 ms。剔除启动阶段入队的报文后，P99 仍约为 3.550 ms。种子 101、Alloc-ID 102 在 Poll4 目标帧 103 已知为 0，未覆盖 FIFO 是 **34800 B**；下一决策采用新 REPORT-only 后已知变为 **34800 B**，重获 **3600 B** 授权（原始日志第 **48155、48713、48722** 行）。结果支持 T2 对报告反馈机会敏感。现有轮询基线已达全局每帧一次，本实验没有测量比基线更快的轮询，也未单独改变传播时延。

## 配对 P99 报文的逐事件证据

三个种子的 SI1/RR 尾包并集共有 182 个不同的「种子、包 ID」组合。两个策略各导出一次，包含其在对方策略中的等待和按原始日志行号追溯的事件。以下为可以直接复核的例子。

1. **额度限制有直接证据。** 种子 101、Alloc-ID 202、报文 **15750** 在 **48920000 ns** 入队。SI1 记录 **18** 个前序包，连续六次 3600 B 的实际装载都被前序包用满，直到 **49898245 ns** 才装载目标包，等待 **978245 ns**。其中在 **49375000 ns** 的决策中，MFU 已知 **18000 B**，超过包含本包的 FIFO 前缀 **15600 B**，所以这一机会可以排除报告看不见需求。实际只装载前序包 15555、15568、15570。RR 中同包入队时有 **8** 个前序包，一个 10800 B 窗口装下前序包及本包，于 **49277085 ns** 装载，等待 **357085 ns**。原始 SI1 日志第 **200549** 行为决策，第 **200675** 行为装载。
2. **REPORT 滞后有直接证据。** 种子 202、Alloc-ID 102、报文 **4509** 在 **14397000 ns** 入队。SI1 为目标帧 **117–124** 连续八次记录 `NO_DEMAND`，有效已知为 0，且无前序尚未装载的预约，离线未覆盖 FIFO 从 **3600 B** 增至 **22800 B**。目标帧 125 的决策使用新到达的 REPORT-only 快照，已知需求升至 **22800 B**；该报文就在这笔授权的首个窗口于 **15640565 ns** 装载，等待 **1243565 ns**。配对 RR 在目标帧 118 装载，等待 **364725 ns**。SI1 的原始入队、连续状态区间和最终装载可查第 **56738、57189–60739、61848** 行。这一等待发生在已有业务运行期间。
3. **在途授权扣减和 RR 等结算均有直接事件记录。** 种子 101、Alloc-ID 202、报文 **6539** 在 RR 的目标帧 169 决策中，原始 REPORT 为 **14400 B**，未结算 D425 扣 **4800 B** 后仍有 **9600 B** 已知需求。此前预算 4800 B 只装下四个前序包，本包所需 FIFO 前缀为 **6000 B**。此时 RR 因未结算跳过该对象。D425 在 **21040950 ns** 结算，之后首个无在途预算的决策仍未授权本包，最终于 **21379045 ns** 装载。可直接确认目标帧 169 被跳过，后续等待涉及其他帧。RR 日志第 **72950、73359、73424、73491、74717** 行依次给出报告、可见需求、前序装载、结算及本包装载。配对 GIANT 等待 **329085 ns**，RR 等待 **806045 ns**。
4. **BWmap 与时隙等待可以直接分解。** 两组的 BWmap 传播都是 **10000 ns**，并包含在提前一帧规划的等待内，不能再额外叠加。报文 15750 在 GIANT/RR 的总 FIFO 等待分别为 **978245 / 357085 ns**。其中入队到各自预算决策为 **830000 / 205000 ns**，决策到目标帧开始均为 **125000 ns**，帧首到实际装载是 **23245 / 27085 ns**。对应差值主要发生在预算形成之前。装载到该包实际开始串行化的时间在 CSV 中另列。

SI1 自身 97 个 P99 尾包中，75 个至少遇到一次前序包用完 3600 B 的装载，76 个至少遇到一次决策时已知需求为 0 且自身仍在未预约 FIFO 中，57 个同时具备这两类证据。RR 自身 98 个尾包中，有 71 个出现同口径可见性差距，9 个出现“本包未被前序预算覆盖、有效已知为正、对象有未结算预算且未获新授权”的状态。两组有 13 个 ID 同时在各自 P99 尾部。每包次数分别在 `full_cap_fills_ahead`、`zero_known_subject_uncovered_frames`、`positive_known_subject_uncovered_outstanding_frames` 中给出。计数表示证据覆盖的报文范围，不能相加为等待时长或视为互斥归因。

**定位结论**　GIANT SI1 的尾部来自报告可见性与每次服务批量限制的叠加。底层提前一帧与 BWmap 时序两组相同，逐帧核对没有发现 GIANT 在保障阶段因总帧容量而少授 T2 已请求的字节。SI2 以稍高的平均等待换取略低的 P99，仍未达到 RR 的 P99。较慢轮询让尾部显著恶化，支持反馈时效是重要因素。仅凭这组对照无法估计固定 RR/GIANT 尾差中每种机制的因果份额。复核入口为 [GIANT 计数和额度分配](../../src/main/java/edu/suda/fttr/dba/GiantDbaPolicy.java#L116)、[需求账本扣减](../../src/main/java/edu/suda/fttr/entity/PonDemandLedger.java#L42)、[RR 在途筛选](../../src/main/java/edu/suda/fttr/dba/MultiGrantRoundRobinDbaPolicy.java#L53)、[轮询和 BWmap](../../src/main/java/edu/suda/fttr/link/PonUplink.java#L463)。

## 复现与文件

在仓库根目录使用 JDK 11+、Maven 和 Python 3.10+。Maven 依赖尚未缓存时可去掉 `-o`。

```powershell
mvn -o -DskipTests package
python -B tools/run_pon_t2_tail.py
python -B tools/plot_pon_t2_tail.py
mvn -o '-Dtest=GiantDbaPolicyTest,GiantCompletionTest,GiantPipelinedLedgerTest,PonReportPollingTest' test
```

分析本次已有日志时可运行 `python -B tools/run_pon_t2_tail.py --reuse-raw`。12 组 Java 仿真使用同一构建，种子 101、202、303 的每组输入分别为 31885、31758、31643 包，逐包核对通过。SI1 和 RR 的新日志还逐种子匹配上轮相应日志的 SHA-256。原始日志及其校验回执保存在结果目录下的 `raw/`，可从实际配置重新生成。专项 Maven 测试共 25 项，全部通过。本轮验证范围为相关回归与配对仿真实验。
