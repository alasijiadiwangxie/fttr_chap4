# 第 17 步 · RR 与 GIANT DBA 性能对比

## 实验设置

使用两台 SFU、每台一台 STA 和三条 T-CONT 队列，共用一条 2500 Mb/s 上行链路。无线侧使用固定 0 μs 时延，测量聚焦于上行 DBA。光帧周期为 125 μs，上下行传播分别为 10.025 μs 和 10 μs。每帧轮询一个 Alloc-ID，64 B 控制窗口占 205 ns。BWmap、REPORT 和需求账本均开启。

| T-CONT | Alloc-ID | 业务 | 生成比例 | SImax / ABmin | SImin / ABsur | 两台 SFU 的 GIANT 名义上限 |
| --- | --- | --- | ---: | --- | --- | ---: |
| Type 2 | 101、201 | VO | 20% | 2 帧 / 4800 B | — | 307.2 Mb/s |
| Type 3 | 102、202 | VI | 35% | 2 帧 / 2400 B | 4 帧 / 4800 B | 307.2 Mb/s |
| Type 4 | 103、203 | BE、BK | 45% | 预留字段 | 4 帧 / 4800 B | 153.6 Mb/s |

低、中、高档总负载目标为 200、700 和 1400 Mb/s，分别相当于物理线速的 8%、28% 和 56%。这里的高档根据**配置额度**选择。其 Type 3 和 Type 4 的目标输入已超过相应 GIANT 名义上限。每台 STA 分担一半业务，VO、VI、BE、BK 各由独立泊松流产生，BE、BK 分别占总输入的 30%、15%。报文统一为 1200 B，各流到达率为配置速率除以每包 9600 bit。

使用三组种子标签 101、202、303。STA 的种子取标签乘以 1000 再加 STA ID。同一档、同一种子的 `rr-multi` 与 `giant` 配置只改变模式。脚本逐项比较 Java 生成的报文 ID、到达时间、源 STA、业务类型和长度，并记录输入 SHA-256。中档另做两组 GIANT 敏感性对照，分别将两条 Type 4 队列的 SImin 从 4 帧降为 2 帧，或将 ABsur 从 4800 B 提高到 7200 B。每次只改一项参数，沿用同一组输入。

## 时间窗口与统计口径

| 时间范围 | 用途 |
| --- | --- |
| `0 ≤ t < 15 ms` | 业务生成和主观察窗口，纳入启动阶段。主吞吐量、时延、队列和占用率统一按此窗口统计。 |
| `15 ms ≤ t < 18 ms` | 停止发流，允许既有队列继续上报和获授权。此期间交付计入收尾交付。 |
| `t ≥ 18 ms` | 停止创建新授权，允许已安排时隙、传播及结算完成。由于最后一次决策可能预留 18 ms 起的目标帧，最终交付与结算的共同上界为 18.135025 ms。 |

- 主吞吐量取窗口内 MFU 交付字节乘 8 除以 15 ms。端到端时延取报文生成至 MFU 交付，主时延只使用窗口内交付的报文。逐包表同时记录收尾交付。P95 采用最近秩。报告同时列示积压，避免把重载时尚未交付的长等待报文排除后误读为时延改善。
- 纯 FIFO 等待从 PON 入队算至授权装载移出队列。PON 发送前等待算至该包 DATA 开始，包含装载后等待同一预算中更早报文发送的时间。FIFO 队长和字节数按入队、装载事件做时间积分。截止时还未交付的报文可处在 FIFO、无线等待或在途阶段，CSV 分列状态。
- DATA 实际发送时间、预算预留时间和 REPORT-only 控制时间按各区间与主窗口的交集计算。物理利用率为实际 DATA 加控制时长除以 15 ms。每 Alloc-ID 给出 DATA 对共享链路的占用贡献，控制时间只汇入 TOTAL。未用预算字节以主窗口内结束的完整 DATA 时隙为集合，使用结算值。跨边界时隙仍按交集计入时间占用。
- REPORT Age 在主窗口内每次 DBA 决策时采样，值为当时 MFU 可见的最新快照距采样时刻的时间。统计已知样本的均值和 P95，另列 UNKNOWN 样本数及已知覆盖率。
- 最终守恒按报文 ID 核对。生成包数等于主窗口交付、收尾交付、显式丢包、最终未交付积压的合计。未用预算对应窗口内没有实际发送的容量，原报文可继续排队。实际丢包以终止丢包事件为准。

## 结果

运行了 **24 个正式场景**，其中 18 个是 RR/GIANT 基线对照，6 个是 GIANT 敏感性对照。9 组负载和种子组合的输入逐包一致，敏感性试验的输入也与各自基线一致。中档 GIANT 基线对三个种子分别重放，Java 日志逐字节一致。共导出 168 行指标和 24666 条交付记录，其中逐包 CSV 包含收尾期交付。

每格依次给出 **吞吐量（Mb/s）/ P95 端到端时延（ms）**。Type 统计在同一种子内先合并两台 SFU 的实际交付报文再计算分位数。每个 Alloc-ID 的报告年龄、未用预算和队列指标见 `metrics.csv`。

### 中档 Type 4 的 SI/AB 敏感性

| 设置 | 观察到的同一 Alloc-ID 最短授权间隔 | 两台 SFU 名义上限 | 主窗口吞吐量 | P95 端到端时延 | 平均 FIFO 队长 | 最终积压 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| SImin=4，ABsur=4800 B | 4 帧 | 153.6 Mb/s | 145.92 Mb/s | 7.670 ms | 135.21 包 | 215.33 包 |
| SImin=2，ABsur=4800 B | 2 帧 | 307.2 Mb/s | 284.80 Mb/s | 1.763 ms | 32.60 包 | 0 包 |
| SImin=4，ABsur=7200 B | 4 帧 | 230.4 Mb/s | 218.88 Mb/s | 4.490 ms | 80.74 包 | 77.33 包 |

缩短 SImin 后，三个种子的 Type 4 最短授权间隔都从 4 帧降到 2 帧，收尾期均清空。只提高 ABsur 时，间隔保持 4 帧，每轮可发送更多报文，积压减小但仍存在。Type 2 和 Type 3 的配对吞吐量与时延一致。本组数据能分别验证 SI 对服务时机的作用，以及 AB 对每次服务字节上限的作用。

## 验收与交付

增量运行 **101 项** DBA、REPORT、BWmap 和 EDCA 关键测试，全部通过。最终执行一次 `mvn -o clean package`，**290 项全部通过**。本阶段修改集中于场景配置、日志分析和导出脚本。

脚本将逐包发流、装载、发送和交付与 Java 汇总对账，验证每笔预算收发和结算的因果顺序，以及 DATA 与控制预留不重叠。对导出的 CSV 再独立按报文 ID 复算 168 条指标的交付量、P95、吞吐量及实际发送时长，检查结果一致。

## 复现

在仓库根目录执行，使用 JDK 11 或更高版本、Maven 与 Python 3.10+。`-o` 要求本机已缓存 Maven 依赖。

```powershell
# 开发时运行 GIANT、关键 PON 和 EDCA 专项
mvn -o "-Dtest=GiantDbaPolicyTest,GiantDbaExecutionTest,DbaPolicyTest,TcontBandwidthTest,PonDbaExecutionTest,PonDbaShadowTest,PonDemandLedgerTest,PonMultiGrantDbaTest,PonReportPollingTest,PonUplinkBwmapTest,EdcaAcceptanceTest" test

# 最终完整回归并打包
mvn -o clean package

# 用 Java 实际运行全部配对场景，生成配置和 CSV
python -B tools/run_pon_dba_comparison.py

# 单独查看一组原始事件
java -jar target/fttr-chap4-0.1.0-SNAPSHOT.jar results/pon-dba-comparison/configs/mid-101-giant.properties
```

输出位于 `results/pon-dba-comparison/`。其中 `metrics.csv` 保存按计量对象统计的指标，`packet-delay.csv` 保存逐交付报文的时间和时延，`run-manifest.csv` 对应每份实际运行配置、种子、输入哈希、重放检查及 Type 4 授权间隔。所有 CSV 由脚本解析实际 Java 输出生成。
