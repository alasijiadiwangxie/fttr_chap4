# 第 18 步 · GIANT 带宽保障与 QoS 验收

`fiber.uplink.dba.mode=giant-complete` 使用固定、保障、非保证和尽力而为四个阶段。规划读 MFU 已收 REPORT 和需求账本。校验后，预算经现有 BWmap 下发，SFU 在对应窗口装载本地 FIFO 的完整报文，通过现有 DATA 和结算事件完成记账。与 `rr-multi` 切换时可用同一套业务和物理配置。第 16–17 步使用的 `giant` 仍可用于重放原实验。

## 规则及来源

经典 GIANT 提供周期性固定与保障阶段，以及受 SI、AB 和需求限制的剩余阶段。这里沿用 Leligou 等人图 2 的周期到期重置，并将两个剩余阶段统一定义为帧首计数达到 1 时有资格。X-GIANT 的参考点是每轮推进所有对象的计时器、到期服务使用下一可用上行帧，以及短 SI 的实验设置。实际 BWmap 提前一帧、REPORT-only 轮询和流水账本是本项目的控制时序。[经典 GIANT，2006](https://onlinelibrary.wiley.com/doi/10.1002/dac.761) · [Arokkiam 等，X-GIANT，2015](https://ieeexplore.ieee.org/document/7248454)

固定 → 保障 → 非保证 → 尽力而为的层级参考 ITU-T G.987.3 第 7 章。Type 5 的四组件独立计数是项目扩展，使用本项目的 SI/AB 配置和合并窗口语义。[ITU-T G.987.3 (05/2025)](https://www.itu.int/rec/T-REC-G.987.3-202505-I/en)

| 类型 | 固定 | 保障 | 非保证 | 尽力而为 |
| --- | --- | --- | --- | --- |
| 1 | `si.fixed.frames` / `ab.fixed.bytes` | — | — | — |
| 2 | — | SImax / ABmin | — | — |
| 3 | — | SImax / ABmin | SImin / ABsur | — |
| 4 | — | — | — | SImin / ABsur |
| 5 | 固定字段 | SImax / ABmin | SImin / ABsur | `si.be.frames` / `ab.be.bytes` |

上述键均置于 `fiber.uplink.tcont.alloc.<id>.` 下。已有键为 `si.max.frames`、`ab.min.bytes`、`si.min.frames`、`ab.sur.bytes`。Type 1 只配置固定一对，其他服务字段省略或填 0，Type 5 四对参数都须为正。Type 4 的 SImax/ABmin 保留兼容字段，DATA 额度只来自尽力而为阶段。

1. **计时。** 首次规划时从各自 SI 开始，0 表示该阶段未启用，>1 时本帧等待并在结束时减一，1 时有资格。固定与保障到期后按周期重置。非保证与尽力而为到期后，有正额度才重置，资源不足或无需求时保持在 1。未用 AB 不滚存到下一周期。
2. **分配。** 每轮先扣 REPORT-only 控制预留。固定到期即预约，不依赖需求。保障到期预算取 ABmin 与当时可见的剩余有效需求两者的较小值。非保证和尽力而为再以各自的 AB 和剩余纳秒为上限。保障无需求时不占窗口，剩余时间可由低级阶段使用。固定预约即使为空仍保留时隙。已发出的窗口实际欠填时，通过结算修正账本，原帧不二次重排。
3. **同级处理。** 固定和保障按类型、Alloc-ID 定序。准入已为所有到期额度留出容量。非保证、尽力而为各自轮转。容量受限时，下一轮从本轮首个获预算对象之后开始，避免始终让同一队列拿到放不下整包的尾部预算。跨级仍遵从严格优先级。
4. **合并与执行。** 同一目标帧每个 Alloc-ID 至多一个窗口。在同一对象追加额度时，只消耗合并后增加的串行化时间。统一校验器检查容量、重叠、额度与归属。窗口按该对象首次获正额度的顺序排列，内部是一个 FIFO 装载窗口。阶段顺序是**决策顺序**，已合并窗口中的报文没有单独的阶段标签。

```text
T(B) = ceil(B × 8000 / rateMbps) ns，T(0) = 0
可追加字节 = floor((帧剩余 ns + T(当前对象总额度)) × rateMbps / 8000) − 当前对象总额度
准入 = T(轮询字节) + Σ(按 Alloc-ID 计算的 T(固定 AB + 保障 AB)) ≤ 帧长
```

准入保守地假设所有额度同时到期，且同帧有一笔轮询。超出容量时配置拒绝启动，报错 `GIANT SLA infeasible`。准入核对的是能否提供配置的预约机会，业务实际吞吐和时延还取决于已知需求、报告延迟及整包装载。

## 流水账本和边界

完整模式允许同一 Alloc-ID 对不同未来帧持有未结算的预约。账本按目标帧和时隙检查顺序、重复及重叠。计算有效需求时，若新快照早于某预约的开始，未结算预约按全部字节扣减，已结算预约按实际字节扣减。快照已经包含装载造成的队列变化时，账本不再为该预约扣减。旧快照与重复结算不会回退最新状态。新的动态预算受扣减后的已知需求限制，只有配置的纯固定部分可以在 UNKNOWN 或已知需求不足时预约。

SFU 根据实际队首装载，报文放不进时停在该队首。结算区分计划、实发和未用。当前模型省略 TC/XGEM/BWmap 字段编码、真实 DBRu、FEC、保护间隔、突发前导、测距补偿和每 ONU 的物理突发数限制。固定空窗没有被计算为真实 DATA 发送，也没有模拟填充报文。该模式以受限 REPORT 视图验证调度保障，不给出全业务的绝对时延承诺。

## QoS 的判定口径

过载组总配置输入为 3020 Mb/s，VO 280、VI 140、BE+BK 2600 Mb/s。两台 SFU 各接一台 STA，各有 Type 2、3、4 队列。每台 SFU 的 VO 对应 Type 2，SImax=1、ABmin=2400 B。VI 对应 Type 3，SImax=1、ABmin=1200 B，另有 SImin=1、ABsur=1200 B。BE、BK 共用一个 Type 4，SImin=1、ABsur=38400 B。两台 SFU 的 VO 和 VI 名义保障额度分别为 307.2 和 153.6 Mb/s。同帧全部保障加控制共需 23245 ns，符合 125000 ns 帧容量。总业务负载超线速与保障配置不可行是两项不同的检查。

上行速率 2500 Mb/s、固定无线时延 0、每帧一个 64 B REPORT-only 预留（205 ns）、上下行传播时延分别为 10.025 与 10 μs。每条泊松流使用 1200 B 报文。种子标签 101、202、303 依次配对，脚本逐包核对生成时刻、ID、源、AC 和大小，并核验属性只有策略键不同。固定种子还执行完整日志重放。过载组在 `[0,10 ms)` 发流与观察，在 `t<12.5 ms` 继续规划，之后完成已经授权的传输和结算。突发组窗口分别截止 3.5 ms、4 ms，上行传播 320 μs。实际丢包以终止丢包事件为准。停调度时队列剩余的数据保留为 pending。

- **保障满足率。** 固定到期额度计入分母。保障到期时，分母取 ABmin 与扣除本轮固定及既有预约后可见需求的较小值。UNKNOWN 的到期机会单列。分别统计发出的保障字节和由真实 DATA 实发量归因的保障字节。在同一合并窗口内，归因按固定、保障、非保证、尽力而为顺序从实际总字节扣除。归因表示组件容量的使用量，报文本身没有阶段标签。
- **服务违约和倒置。** 有应发额度的到期机会未获全额记为授权违约，实际使用不足另列。SI 状态、AB 限制和阶段序号逐帧检查。若某应发固定或保障额度被削减，却给了较低阶段资源，计为倒置。实发间隔和已知积压的连续未服务帧数另列。
- **吞吐与服务质量。** 吞吐用主窗口内实际 MFU 交付量除以共同窗口长度。P95/P99 采用窗口内已交付报文的最近秩，未交付的高等待报文由积压列反映。`packet-delay.csv` 保留每个生成报文，收尾交付有独立窗口标志。
- **利用率与公平性。** 共享上行物理利用率以实际 DATA 加 REPORT-only 占用计算，另列预留与未用预算。Jain 指数按同一次运行中同类型 Alloc-ID 的实际交付吞吐计算，并联查持续积压和实际服务间隔。

## 验收结果

新增 11 项 Maven 测试，覆盖四阶段、Type 5 独立计时、尾部预算轮转、额度复用、非法配置、固定 UNKNOWN、流水与迟到快照、同刻装载边界、重复与重叠授权。增量 **100 项通过**，完整 `mvn -o clean package` **301 项通过**，含既有 290 项，失败、错误、跳过均为 0。

用最终 JAR 重放第 16 步的授权与决策轨迹及第 17 步的 24 组 RR/GIANT 对照。两阶段的归档 CSV 均逐字节一致。本阶段 22066 条报文记录按场景和 ID 唯一，包含 18887 次实际交付和 3179 条未交付积压。交付记录均满足交付时刻减生成时刻等于端到端时延。

三组过载配对的结果如下，表值为种子间均值。两种策略的输入逐包一致。

| 策略 | Type 2 吞吐（Mb/s） | Type 3 吞吐（Mb/s） | Type 4 吞吐（Mb/s） | 总吞吐（Mb/s） | DATA+控制利用率 | P95 / P99（ms） | 收尾后积压（包） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 完整 GIANT | 268.48 | 136.64 | 1855.36 | 2260.48 | 90.69% | 2.868 / 3.088 | 152.33 |
| RR 多授权 | 267.52 | 134.40 | 1331.84 | 1733.76 | 69.63% | 4.872 / 5.430 | 906.33 |

完整 GIANT 中，Type 2 的 432 个有已知需求的到期机会合计需保障 1006800 B，Type 3 的 263 个机会需 315600 B，均获得全额且由实际发送字节覆盖。保障授权违约与倒置为 0。Type 2/3 另有 21/27 个 UNKNOWN 到期机会，收尾后积压均为 Type 4。两台 SFU 的 Type 4 均持续有待处理业务，同级 Jain 指数为 0.99921–0.99951，两次实发之间最多相隔 2 帧。观察到的吞吐提升同时包含流水授权与协议阶段的影响，RR 对照使用其原有的单笔未结算规则。保障结论来自阶段、资格和实际 DATA 三方核对。

资源复用实验沿用种子 101 的相同 BE/BK 输入，去掉 VO/VI 后，Type 4 主窗口吞吐由 1880.64 增至 2248.32 Mb/s，最终清空。过载和该对照均无显式丢包。故意超配的配置需要 134605 ns（含控制），超过 125000 ns，Java 启动时拒绝。

混合突发组注入 268 包，主窗口交付 191 包，收尾再交付 74 包，最终积压 3 包。Type 1 在首两帧 REPORT 仍未知时各实发 1200 B，之后观测到 1800 B 队首阻塞 1200 B 固定窗口。Type 1 固定预约满足率为 100%，窗口内有 24 次未用足固定额度，其中包括无报文可发的时隙。Type 5 在帧 7 合并了 1200 B 固定、2400 B 保障、2400 B 非保证、1200 B 尽力而为，D8 实发 7200 B，窗口 879045–902085 ns，结算于 1222085 ns 到达。本组物理利用率为 23.63%，反映间歇到达、控制传播与周期额度。

## 复现

在仓库根目录使用 JDK 11+、Maven 与 Python 3.10+。若本机未缓存 Maven 依赖，可移除 `-o`。

```powershell
mvn -o "-Dtest=GiantCompletionTest,GiantPipelinedLedgerTest,GiantDbaPolicyTest,GiantDbaExecutionTest,DbaPolicyTest,TcontBandwidthTest,PonDbaExecutionTest,PonDemandLedgerTest,PonMultiGrantDbaTest,PonReportPollingTest,PonUplinkBwmapTest" package
mvn -o clean package
python -B tools/run_pon_giant_completion.py
java -jar target/fttr-chap4-0.1.0-SNAPSHOT.jar results/pon-giant-completion/configs/overload-3020-101-giant-complete.properties
```

输出至 `results/pon-giant-completion/`。`run-manifest.csv` 登记 8 次成功运行、1 次预期拒绝、各输入哈希及实际配置。`giant-grant-trace.csv` 有 4313 条逐帧逐 Alloc-ID 记录，`giant-qos.csv` 有 55 条统计，`packet-delay.csv` 有 22066 条报文结果。最终 JAR 重放后，5 份 CSV 的 SHA-256 均一致。
